# My Flows Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A person can make several named flows — their own chanting order built from the app's sections — and chant them in the existing reader, while every original reading stays exactly as it is.

**Architecture:** A flow is stored as a name plus an ordered list of section references (`namo.flows.v1`). One function turns a flow into a `Reading` at the moment it is shown, reusing the content's own text objects; the reader, the position store and Home's Continue card all look readings up through one resolver that understands both content ids and flow ids. New surfaces (Library part, editor page, sheets, Home row) are built from the existing design widgets.

**Tech Stack:** Flutter 3.47.9, flutter_riverpod (Notifier), go_router, shared_preferences via `KeyValueStore`. No new packages.

**Spec:** `docs/superpowers/specs/2026-11-10-chanting-flows-design.md` (approved 2026-11-10). The spec was written before Pirith existed; the "Rulings" below record where this plan departs from its section 7 and why.

## Global Constraints

- Verse text is never copied as new strings, changed or typed by hand. A flow stores only references (reading id + section id).
- Nothing is fetched at run time; no new packages; no payments, ads or prompts.
- Built from the shared parts in `lib/design/widgets/` (`NamoPage`, `PageHeader`, `ListRow`, `SurfaceCard`, `SheetFrame`, the buttons in `buttons.dart`, `EmptyState`) and `lib/design/tokens.dart` (palette roles, `NamoSpace`, `NamoRadius`, `NamoMotion`, `NamoSizes.touchTarget` = 48). No hard-coded colours, no text under 12, every target at least 48 × 48, both themes.
- Existing saved data (`namo.settings.v1`, `namo.saved.v1`, `namo.position.v1`) keeps its format. Every existing address keeps working.
- The original readings are never altered by any flow operation; `Library` objects are never mutated.
- Android, iOS and web together: no platform-specific code.
- Exact copy (from the spec): "My flows", "Make your own flow", "Choose the sections you chant, in your order.", "New flow", "Name", "Start from", "Nothing", "Create", "Edit flow", "Remove from flow", "Removed", "Undo", "Move up", "Move down", "Add sections", "Start chanting", "This flow has no sections yet.", "Delete flow", `Delete "<name>"? - Name rule: ends trimmed, at most 40 characters (longer input is cut to 40 after trimming), empty becomes "My flow", then "My flow 2", "My flow 3" … (the first of these not already used as a name). Two flows may otherwise share a name.
- Flow ids are `flow-1`, `flow-2` …, never reused.

## Rulings (departures from the spec's section 7, made because Pirith now exists)

1. **Ids inside a flow are composite, not globally unique.** Every pirith has one section with id `p` and verses `b1`, `b2` …, so section and verse ids repeat across readings. Instead of renaming content ids (which would churn checked content and its tools), the reading made for a flow gives each section the id `<readingId>~<sectionId>` and each verse the id `<readingId>~<verseId>`. The spec's build-tool uniqueness check is replaced by a test that no content id contains `~` and no reading id starts with `flow-`. Cost if wrong: one function to change.
2. **"Object-for-object" means the text objects.** Flow verses are new `Verse` values with a new id whose text strings, `phrases` list, notes and corrections are the identical objects of the original.
3. **Pirith sections can be added to a flow.** They show as passages (as in a pirith) with no recording, no chant highlight, and no bookmark button (a pirith has none today). A flow is always moved through section by section with Previous/Next, even when it holds only pirith.
4. **Back from a flow** opened from the Library goes to the Library (`/library`); from the editor to the editor; from Home to Home.

## Review Focus

- A very long pasted name (500 characters, with line breaks) → stored name is at most 40 characters, single line, no overflow at 320 wide with 2× text. (Task 1 name rule test; Task 5 sheet test.)
- A flow that holds only pirith sections → Previous/Next still move between its sections; no recording bar; no favourite button. (Task 3.)
- Stored flow refers to a section the content no longer has → that one section is skipped everywhere (reader, editor count, Library count); the rest of the flow is intact and the stored flow is not rewritten. (Tasks 2, 4, 5.)
- The remembered section was removed from the flow, or the flow was emptied or deleted while it is Home's "Continue reading" → reader opens from the start; an empty or deleted flow is not offered on Home and its address shows the not-found page. (Tasks 3, 6.)
- Mixed flow (ordinary sections and pirith sections) with both languages, "Section by section" layout → every section shows its own text exactly once, in flow order, and the place survives a language change. (Tasks 2, 3.)

/// Trimmed, line breaks turned to spaces, cut to 40; empty gives "My flow",
/// "My flow 2" … (first not in [taken]).
String flowName(String raw, Iterable<String> taken);
/// "0 sections", "1 section", "N sections".

  void insert(String id, int index, FlowRef ref); // Undo; index clamped; no-op if present
  void move(String id, int from, int to);         // `to` is the final index; out of range is a no-op
}
final flowsProvider = NotifierProvider<FlowsController, FlowsState>(FlowsController.new);
